I spent the last couple of weeks writing FlashAttention from scratch — starting with the forward pass in raw CUDA — because I wanted to *feel* the thing everyone repeats about it: that it's fast because it's "IO-aware." I'd read the sentence a dozen times and could recite it, but I couldn't have told you where, in an actual kernel, the win shows up.

Short version: that one sentence is hiding two completely separate problems. Tiling the attention so it never materializes the score matrix fixes memory — and it made my kernel **11× slower**. Getting it actually fast is a different fight entirely, one that has almost nothing to do with the online-softmax trick everyone teaches. This post is the first half: the memory wall, the algorithm, and getting a correct forward kernel. The "why is it still slow" autopsy is the next post.

For context: this is part of a [summer I'm spending](/blog/blog-motivation) going deep on ML systems after work. The last two weeks were GPU and CUDA fundamentals and then attention internals — mostly out of [GPU MODE](https://www.youtube.com/@GPUMODE) lectures, Stanford's [CS336](https://stanford-cs336.github.io/), the PMPP book, Horace He's [Making Deep Learning Go Brrrr](https://horace.io/brrr_intro.html), and the FlashAttention papers ([FA1](https://arxiv.org/abs/2205.14135), [FA2](https://arxiv.org/abs/2307.08691)) plus Tri Dao's blog. It's one thing to read how a GPU works and another to make one go fast, and the only way I trust myself to tell the difference is to build the thing and measure it.

Everything here ran on a single **A100-SXM4-80GB** (108 SMs, 2.0 TB/s HBM, 312 FP16 tensor-core TFLOP/s) on Lightning AI. Every TFLOP/s number below is the attention FLOPs at `B=8, H=16, d=128`, fp16, non-causal, timed with CUDA events; "SDPA" is PyTorch's flash backend on the same shapes.

## The memory wall, measured

Before writing a single kernel I wrote the naive baseline, because you can't appreciate the fix without feeling the problem:

<CodeCard file="naive.py">
```python
def naive_attention(q, k, v):
    # q,k,v: [B, H, N, d]
    d = q.shape[-1]
    scale = 1.0 / math.sqrt(d)
    s = (q @ k.transpose(-2, -1)) * scale   # [B, H, N, N]  <- the problem
    p = torch.softmax(s, dim=-1)
    return p @ v
```
</CodeCard>

That `[B, H, N, N]` scores tensor is the whole story. At `B=8, H=16, N=8192` in fp16 it's `8·16·8192·8192·2` bytes = **17 GB** for one intermediate — and softmax reads the scores to write the probabilities, so both are resident at once and you're holding it twice. I swept sequence length and watched it climb:

<MemoryWall />

Even on an 80 GB A100, naive attention falls over at `N=16384` — the scores are ~69 GB on their own, and ~137 GB once softmax holds the second copy. The memory grows as O(N²) and there's no batch size small enough to save you, because the problem is one sequence, not the batch.

FlashAttention's claim is that you never materialize that tensor at all. You tile it, keep a running softmax, and the memory drops from O(N²) to O(N). I'll come back to whether that's also what makes it *fast* — it isn't, and that surprised me.

## The algorithm in one paragraph

Online softmax (Milakov & Gimelshein, [2018](https://arxiv.org/abs/1805.02867)) lets you compute a softmax in a single streaming pass with a running max `m` and running denominator `l`, rescaling the partial result whenever the max moves. FlashAttention ([Dao et al. 2022](https://arxiv.org/abs/2205.14135)) wraps that in a tiling loop: load a block of Q, stream blocks of K and V through fast on-chip SRAM, accumulate the output block as you go, and never write the scores to HBM. I'm not going to re-derive it — the [paper](https://arxiv.org/abs/2205.14135) and [GPU MODE Lecture 12](https://www.youtube.com/watch?v=zEuwuCTEf_0) do it better than I can. What I want to talk about is what happened when I built it.

Here's the whole algorithm in plain PyTorch, which I wrote first as a numerical oracle to check the CUDA against. It streams K/V in blocks and never holds more than one block of scores:

<CodeCard file="tiled_ref.py">
```python
def tiled_attention(q, k, v, block_k=128):
    B, H, N, d = q.shape
    scale = 1.0 / math.sqrt(d)
    m   = torch.full((B, H, N, 1), float("-inf"))   # running max
    l   = torch.zeros((B, H, N, 1))                  # running denom
    acc = torch.zeros((B, H, N, d))                  # unnormalized output
    for j in range(0, N, block_k):
        kj, vj = k[:, :, j:j+block_k, :], v[:, :, j:j+block_k, :]
        s = (q @ kj.transpose(-2, -1)) * scale       # [B,H,N,bk] — one block of S only
        m_new = torch.maximum(m, s.max(dim=-1, keepdim=True).values)
        alpha = torch.exp(m - m_new)                 # rescale factor when the max moves
        p = torch.exp(s - m_new)
        l   = alpha * l   + p.sum(dim=-1, keepdim=True)
        acc = alpha * acc + p @ vj
        m = m_new
    return acc / l        # divide by l once, at the very end (the FA2 choice)
```
</CodeCard>

Dividing by `l` once at the *end* — keeping the accumulator unnormalized through the whole loop — is one of the choices that separates FlashAttention-2 from -1 (the bigger one is the loop order, which the CUDA kernel further down uses). I'll come back to both.

## Win #1: tiling fixes memory (and made it 11× slower)

The first real kernel is the dumbest thing that tiles correctly: one CUDA thread per query row, K and V staged into shared memory a block at a time, the online-softmax recurrence done in scalar floating-point. One thread to a row means the arithmetic runs on the general-purpose CUDA cores and the tensor cores sit idle the whole time. That's on purpose — the point was to isolate *memory discipline* from *fast compute*, to prove tiling alone fixes the wall and to have an honest "before" for when the tensor cores go in.

<CodeCard file="flash_min.py">
```cuda
for (int j = 0; j < N; j += BLOCK_N) {
    // cooperative load of this K/V tile into shared memory
    // … (every thread helps stage Ks[], Vs[]) …
    __syncthreads();

    for (int kk = 0; kk < BLOCK_N; ++kk) {
        // score for this key: s = scale * dot(qreg, Ks[kk])
        float s = 0.f;
        for (int t = 0; t < HEAD_DIM; ++t) s += qreg[t] * __half2float(Ks[kk*HEAD_DIM + t]);
        s *= scale;

        // online-softmax update for one key (the scalar recurrence)
        float m_new = fmaxf(m, s);          // running max
        float alpha = __expf(m - m_new);    // rescale old state to the new base
        float p     = __expf(s - m_new);    // weight of this key
        l = l * alpha + p;
        for (int t = 0; t < HEAD_DIM; ++t)
            acc[t] = acc[t] * alpha + p * __half2float(Vs[kk*HEAD_DIM + t]);
        m = m_new;
    }
    __syncthreads();   // don't overwrite smem until everyone's done reading this tile
}
```
</CodeCard>

It works. Max abs error vs PyTorch's `scaled_dot_product_attention` is ~1e-3 in fp16, and — the part I actually cared about — it ran `N=16384` at **2.15 GB**, exactly where the naive version OOM'd asking for ~137 GB. O(N) memory, made concrete. That's the whole FlashAttention promise, in one short kernel.

And it runs at **~5 TFLOP/s. The naive baseline does 54** — slow on memory, but its two big matmuls go straight to cuBLAS's tensor-core kernels, which my scalar loop can't touch. Tiling for memory made the kernel **11× slower**.

<Callout type="lesson" title="The thing nobody says out loud">
"FlashAttention is fast" is two claims wearing one coat. *It fits* (O(N) memory, the online-softmax algorithm) and *it's fast* (tensor cores, occupancy, hidden memory latency) are completely separate axes. My tiled kernel nailed the first and was a disaster on the second. Most write-ups collapse both into one sentence and you never find out they're different until you build it.
</Callout>

So the next kernel does the obvious thing — hand those matmuls to the tensor cores myself.

### The bug that taught me what "in shared memory" means

The first version of that inner loop was wrong in a way I find funny in hindsight. I'd carefully staged V into shared memory — and then read it from global memory anyway, with an index variable that wasn't even defined in that scope:

```diff
- acc[t] = acc[t]*alpha + p * __half2float(V[base + (long)kj*HEAD_DIM + t]);  // global; kj undefined here
+ acc[t] = acc[t]*alpha + p * __half2float(Vs[kk*HEAD_DIM + t]);              // the staged smem tile
```

Staging K/V into shared memory does nothing if you then reach past it to global memory. The fix restored the exact reuse the staging was *for*. Small bug, but a clean reminder that "keep it in SRAM" is a thing you have to actually do on every read, not a property the data has once you've copied it.

## Win #2 (the start of it): adding tensor cores

The second kernel keeps everything in registers and shared memory and does both matmuls — `Q·Kᵀ` and `P·V` — on the tensor cores via WMMA, the CUDA API for handing the tensor cores 16×16 tiles as opaque "fragments" and getting their product back. I also switched to the FlashAttention-2 loop order: one warp (the 32 threads a GPU runs in lockstep) owns a block of 16 query rows on the outside and streams the K/V blocks through on the inside, keeping its running `(m, l)` and output accumulator local and normalizing by `l` exactly once at the end.

Before wiring the whole thing together I tested the `Q·Kᵀ` matmul on its own — 1.9e-5 against PyTorch — so that when the fused kernel was wrong I'd know it wasn't the tensor-core fragments or the transpose trick. (You feed K as a column-major fragment, which reinterprets the same row-major buffer as `Kᵀ` with no data movement.)

<CodeCard file="flash_wmma.py" collapsible summary="The FA2-schedule inner loop (WMMA)" lines="40–94">
```cuda
for (int j = 0; j < N; j += 16) {
    // ---- S = Q @ K^T  (WMMA, fp16 in, fp32 accumulate; col_major K = the transpose) ----
    wmma::fragment<wmma::accumulator,16,16,16,float> cs;
    wmma::fill_fragment(cs, 0.f);
    for (int kk = 0; kk < NK; ++kk) {
        wmma::fragment<wmma::matrix_b,16,16,16,half,wmma::col_major> kb;
        wmma::load_matrix_sync(kb, Kb + kk*16, HD);
        wmma::mma_sync(cs, qa[kk], kb, cs);
    }
    wmma::store_matrix_sync(Ss, cs, 16, wmma::mem_row_major);
    __syncwarp();

    // ---- online softmax, one row per lane ----
    if (lane < BM) {
        int r = lane;
        float rowmax = /* max over the 16 scaled scores: scale * Ss[r*16+c] */;
        float m_new = fmaxf(Ms[r], rowmax);
        float alpha = __expf(Ms[r] - m_new);
        float rowsum = 0.f;
        for (int c = 0; c < 16; ++c) {
            float p = __expf(scale * Ss[r*16 + c] - m_new);
            Ps[r*16 + c] = __float2half(p);
            rowsum += p;
        }
        Ls[r] = alpha*Ls[r] + rowsum;  Ms[r] = m_new;  Al[r] = alpha;
    }
    __syncwarp();

    // ---- PV = P @ V  (WMMA over the 8 head-dim sub-tiles) ----
    wmma::fragment<wmma::matrix_a,16,16,16,half,wmma::row_major> pa;
    wmma::load_matrix_sync(pa, Ps, 16);           // the probabilities we just wrote
    for (int nt = 0; nt < NK; ++nt) {
        wmma::fragment<wmma::matrix_b,16,16,16,half,wmma::row_major> vb;
        wmma::load_matrix_sync(vb, Vb + nt*16, HD);
        wmma::mma_sync(pv, pa, vb, /*zero acc*/);  // -> PVs[nt block]
    }
    // ---- O = alpha*O + PV : rescale the running output, then add this block ----
    for (int t = lane; t < BM*HD; t += 32) Os[t] = Al[t/HD]*Os[t] + PVs[t];
    __syncwarp();
}
// normalize once at the very end: O[r] = Os[r] / Ls[r]
```
</CodeCard>

This one is correct too — max abs error vs SDPA between **1.2e-4 and 4.9e-4** across shapes from `N=16` up to `B=4,H=8,N=2048`, both fp16. (A nice surprise along the way: the tiled kernels are *more* accurate than naive, not less — naive came in around 6e-4 — because the running `m`, `l`, and accumulator all live in fp32 even though the inputs are fp16. Tiling done right is a precision win, not a tax.)

So: tensor cores, the real FA2 schedule, numerically correct. The kernel above — one warp, 16 keys per block — runs at **~14.7 TFLOP/s, about 7% of PyTorch's SDPA**, still 3.7× slower than the naive baseline I was trying to beat. Widening the K/V block to 64 keys, so each softmax update is amortized over more work, lifts it to **~21 TFLOP/s (~10% of SDPA)** — and that's where it plateaus.

That plateau is where this post stops and the next one starts. Tensor cores were necessary and nowhere near sufficient, and I had three confident theories about why it was still slow that were all wrong. But before any of that, I have to admit how much of these two weeks was not algorithm at all.

## Correctness was the hard part, and most of it wasn't the math

The online-softmax recurrence is maybe a dozen lines and I had it right early. The time went somewhere much dumber: making sure the kernel I thought I was running was the kernel that ran at all.

### Hours lost to a kernel that never launched

For most of a day my WMMA kernel produced wrong output across about ten different configs — and the *symptoms kept shifting*. Same input, different runs: `0.54`, then `NaN`, then `0.29`, then all zeros. The one pattern was that the garbage depended on the *total allocation size*, not the tensor shape. I went hunting for a numerical bug in the softmax, then an indexing bug, then a race.

There was no compute bug. The kernel had never launched, not once.

<Callout type="lesson" title="Always check the launch before you trust the output">
The launch was failing silently with `cudaErrorInsufficientDriver`: the system `nvcc` was CUDA 13.0, which the host's driver (570) can't run, while torch quietly works because it bundles its own 12.8 runtime. Every "result" I'd been debugging was just the output tensor's *initial* value — uninitialized memory, whatever happened to be in that allocation pool (sometimes garbage, sometimes zeros). **The allocation-dependent NaN was the tell:** it was memory the kernel never touched. One check after the launch surfaces it instantly, and it's the first thing in every kernel harness I write now.
</Callout>

### The GPU changed under me

Earlier, a different impossibility: my memory sweep cheerfully reported a 78.9 GB allocation as "OK" on what my environment check insisted was a 40 GB card. My first instinct was memory oversubscription — host paging making an over-large allocation look like it fit.

It wasn't. The Lightning instance had silently swapped from a 40 GB A100 to an 80 GB one between sessions. The tell was timing: `N=12288` took 1.07s versus `N=8192` at 0.30s — about 3.5×, in line with the 2.25× FLOP ratio plus a memory-bound penalty, and nowhere near the 5–20× slowdown host paging would cause. `torch.cuda` confirmed 85 GB of total memory. The hardware identity I'd written my constants against was just… different.

<Callout type="lesson">
On ephemeral cloud GPUs, re-verify the machine every session, not just the code. The roofline, the memory ceiling, the crossover sequence length — every number I care about is pinned to *which card this is*, and that turned out not to be stable. Re-stamp the constants before trusting a single benchmark.
</Callout>

## Where this leaves us

The forward pass is correct, in three versions that each fix one more thing, and the two wins are cleanly separated:

| kernel | TFLOP/s | what it proves |
|---|---|---|
| naive | 54 | the O(N²) memory wall (OOMs at N=16384) |
| tiled, no tensor cores | 5 | tiling fixes memory (2.15 GB @ N=16384) — and nothing else |
| WMMA, FA2 schedule (best) | 21 | tensor cores are necessary, ~10% of SDPA, not nearly enough |
| PyTorch SDPA (flash backend) | ~200 | the target — 65% of the card's peak |

The algorithm that *is* FlashAttention — the online softmax, the tiling, the O(N) memory — was the easy 10%, and once it was correct it was nearly free. Everything between my 21 TFLOP/s and SDPA's ~200 is a different problem, made of occupancy and memory latency and how the tensor cores are actually fed.

That's the next post: three hypotheses about the gap, all wrong, and what a profiler I wasn't allowed to run finally told me anyway.
