## What the traders were actually betting on

The instrument is a Kalshi-style binary prediction market. Each race tracks four racers, and each racer gets its own market asking "will *this* racer finish best of the four?" You trade YES or NO contracts priced in integer cents on a 1–99 ladder; a YES and a NO always sum to 100¢; when the race ends the market settles to 100 if that racer placed highest and 0 otherwise. Buy YES at 40¢, your racer wins, you're paid 100. The four markets are four answers to one question, so exactly one settles to 100 and the other three to 0, which is what couples them: a price move on one racer is information about the other three.

Underneath each market is a continuous limit order book with price-time priority — limit and market orders, partial fills, cancels, resting liquidity, and a matching engine deciding who trades with whom at what price. On top sit wallets, per-market P&L, and a cumulative leaderboard.

Picture 150 laptops firing at all four books the instant a blue shell knocks the leader out of first. That one event just moved every racer's odds of finishing best, so every market reprices at once. A few hundred milliseconds of lag is the difference between a fill and a miss. The exchange doesn't get to be slow, and it definitely doesn't get to be wrong about who holds what. ## Version one: Python on a deadline

v1 came together fast and on a deadline. I built it with a React frontend, a FastAPI backend, a standalone Python asyncio matching engine, Redis doing double duty as the command bus and the live fanout, and Postgres as the source of truth.

I built it CQRS (Command Query Responsibility Segregation) [explainn concsiely precisely reasnoning why]. `POST /orders` returned `202 Accepted` immediately, without persisting or matching the order: it dropped the command onto a Redis stream and returned. The engine consumed the stream, matched in memory, persisted to Postgres, and published fills over pub/sub; the browser learned what happened when a WebSocket message told it to refetch.

The matching core was correct, but the trouble was all in the plumbing added around it.

### How v1 grew

Each layer I added around the matching core believing to make it faster or more scalable also added a *seam* where two components now had to agree about state. In order:

- **The order book itself.** It started as a `SortedDict`, a balanced tree keyed by price. Simple, and it worked. I later replaced it (more in v2).
- **The two-plane split.** One FastAPI process couldn't own both order entry and the WebSocket fanout under load, so I split it into a control plane and a separate gateway.
- **[title]** I made the engine run purely in memory during a round and bulk-persist only at settlement. That killed the per-order database write on the hot path — the single biggest speedup in v1 [although it trades away recovery for mid round crash, which in our case was acceptable].
- **Sharded fanout.** To keep 150-plus WebSocket clients fed, I sharded the fanout across worker coroutines. They shared a sequence-tracking map with serialized access. [dont mention this bug]

## Where version one broke down

The visible problem was speed, so before the event I load-tested v1 hard. My testing at the time was thinner than it should have been. [rephrase this, essentially testing was insufficient here] I aimed for 1,500 aggregate orders a second — 150 users at ~10/s each, the load I'd designed for — and got a *two-front* failure I couldn't cleanly tell apart.

The first front was my own load generator. I'd written it as a single Python process on one asyncio event loop, opening 200-plus WebSocket connections, firing HTTP order submissions, and draining the inbound flood of book updates and trade notifications, all on one core. Additionally, there was coupling as each simulated user awaited its own HTTP response before sending the next order. So when the server slowed down, my client's send rate collapsed with it and throttled itself to 10–20% of target. So it measured its own ceiling instead of the exchange's.

The second front was underneath: the server was also saturating. At the sub-300 orders a second my client could deliver, one asyncio actor per market (four in all) topped out around **150–286 accepted orders a second**, submit-to-fill p99 between **28 and 78 seconds**, and a backlog that climbed as high as **17,002** queued commands.

## Version two: one thread, no locks

**I gave the whole round to a single engine thread.** One OS thread owns every order book and every wallet, does all the mutation, and never takes a lock, because nothing else touches that state while it's matching. I chose this for determinism, a property I'd learned to want the hard way. Feeding the same sequence of commands in and you get bit-for-bit identical output every time [which is also good for testing? in general should be made clear as well precisely and concisely that v2 was designed to be easily testable at all levels]. In v1, "who traded first" depended on which sharded worker saw a message when. In v2 a single ingress task stamps every command with a sequence number the instant it arrives, and that number is the only clock that matters. Price-time priority means nothing if two components disagree about the time, so I made sure there was only one. [also we should never present things as did this and this, should always be subtly (or not so subtly) demonstrating active thinking, reasoning, tradeoffs, deciison making, best engineering principles and undeerstanding, from first principles through the lagnuage, content, and delivery of the blog]

Commands reach that thread over a lock-free single-producer/single-consumer ring, and events leave over another. The engine busy-spins reading its inbound ring: no async runtime, no scheduler, no futures, just a thread in a loop. A hand-rolled lock-free ring is exactly the kind of thing that's subtly wrong for months, which is why I later model-check it instead of trusting my reading of it.

**The book is a flat array, and nothing allocates on the hot path.** Prices live on the fixed 1–99 cent ladder, so a price level is just an integer in `[1, 99]`, which means a level is an array index. The tree a general exchange would reach for is pure overhead here. I use a 99-slot bucket array instead: O(1) to index a level, a short bounded scan to find the best price, no comparisons and no pointer-chasing.

<ArrayLadder />

Allocation gets the same treatment. Every resting order lives in a pre-sized object pool, and matching relinks slots through an intrusive list rather than asking the allocator for memory. I built it this way on a hunch — allocation was the most likely cause of the latency spikes I'd seen at the event — and when I measured which choices actually mattered, this was the biggest by a wide margin.

<HotPath />

**Durability sits in front of the engine.** I wanted v1's speed — no per-order database write on the hot path — without v1's exposure to losing a round on a crash. So the sequencer hands each command to the journal *before* it pushes it to the engine: nothing reaches the matching thread that isn't already recorded. To keep the disk off the hot path I batch the `fsync`, one flush per 64 commands or a 5 ms timer when traffic is quiet, so the lag stays bounded either way. What this actually guarantees: a command is recorded in intent before it matches, but the physical `fsync` lands with the next batch a few milliseconds later. So a crash can lose up to one batch of already-acked fills. For real money that window would be unacceptable; for a party game where the fallback is re-running the round, it's the right trade, and the ordering is what lets me reconstruct a round by replaying the log at all.

**Risk is the one product decision.** v1 had a flat ±100 position limit and let bots skip it. v2 has a single collateralized risk authority: to hold a position you post collateral equal to your worst-case loss, reserved at order entry before the order can match, settled on each fill, released after, under a per-market cap and a global budget. One deliberate simplification: it reserves per market and never nets across the four coupled racer markets, even though exactly one can settle to 100. Netting the mutual exclusivity would free up collateral a trader can't actually lose, but per-market reservation *only ever over-reserves*, never under, so no one takes a position they can't cover. For a party game, conservative-and-obviously-safe beat capital-efficient-and-subtle. Whether collateral is even the right model here is a separate question I get to at the end.

**The game-specific logic lives behind four narrow traits** — the book, the risk model, settlement, and scoring — so next year's game is four trait implementations and nothing else touched. It's the one abstraction here I'd defend by the "what breaks if I delete it" test, and the answer is a real, planned use: a new game a year should be cheap, not a rewrite.

## Proving it correct

The fast order book has a trust problem. The same cleverness that makes it quick — an intrusive list through an object pool, cached best-price cursors, O(1) relinking — gives a subtle bug a lot of places to hide and produce *almost* the right answer. I didn't want to trust it by reading it. So I wrote a second order book whose only goal is to be obviously correct: resting orders in a flat list, rescanned end to end on every operation to find the best price. It's slow on purpose and shares no code with the fast one. If they shared a matching helper, a bug there would corrupt both identically and I'd never see it. Sharing nothing means any bug in the fast book shows up as a divergence from the slow one.

<DifferentialHarness />

The test feeds both books the same randomly generated command stream and, after every command, checks that they emitted the same events and hold the same resting orders. I made the generator deliberately cruel: a tiny space of four users and a handful of order IDs, so crossing trades and self-trade prevention fire constantly instead of almost never, heavy on cancels, every order type. Each step also checks invariants directly on the fast book — positions net to zero per market, reserved collateral never goes negative, the book is never crossed at rest — so a bug that keeps both event streams equal but corrupts an invariant still gets caught. That's the whole point of making the reference slow and dumb: it shares no cleverness with the fast book, so it can't share a bug, and "is my intrusive-list object pool correct?" becomes "do these two disagree?", which a test answers in seconds.

Determinism gets the same treatment. The engine is a pure function of its sequenced input and the journal records exactly that input, so replaying the log has to reproduce the round bit-for-bit. The test checks that after every command, not just at the end, so a divergence surfaces mid-round while the books are still full. One subtlety: the object pool's physical layout isn't canonical, so two logically identical books can differ byte-for-byte in which slot holds which order. I compare a normalized snapshot of logical state instead — resting orders in price-time order, positions, wallets — so the comparison itself is deterministic.

The ring is the one piece of genuinely subtle concurrent code, so I model-check it with `loom`, which explores all possible thread interleavings and asserts the consumer sees every item, in order, with nothing lost. It checks the real ring: `loom` swaps only the atomics underneath, so the code under test is the code that ships, not a hand-written model that could drift from it. I run it on a tiny two-slot ring because the interleaving space explodes combinatorially; a separate million-item stress test on real threads covers what the tiny model can't reach.

The whole suite is **517 tests** green, and the differential alone runs **600** generated command streams against the reference book. The count isn't the thing I cared about. It was being able to say the money path is checked against an independent reference on every input, instead of trusting it held on the day.

## How fast, and what actually binds it

The numbers, flat: at 20,000 orders a second offered to 250 clients, the engine acks about 18,000 at an in-system p50 of 2 µs and p99 of 33 µs, on a loop averaging ~1.4 µs an iteration, with nothing lost on a client's reliable lane. The ~10% gap between offered and acked isn't loss; it's cancels chasing orders that already filled, which reject. The rate counts acks, not the whole offered stream.

<ThroughputWall />

Two things make those latencies trustworthy rather than flattering. I measure in-system latency on the engine's own clock (ingress stamp to emit stamp), so it's immune to skew between machines and isn't the round trip to a browser. And the load generator is open-loop: it fires on a fixed schedule regardless of when replies come back, so a stall shows up as an inflated tail instead of hiding behind a slower send rate. The rig was AWS `c7a.2xlarge` boxes (8 vCPU, single market). The histograms are power-of-two-bucketed, so every latency here means "at or below that bucket."

The throughput number matters less to me than where the bottleneck actually sat, and finding that meant taking the engine off the wire entirely.

So I ran the matching loop in-process, feeding it commands directly with no network, no egress, and no journal on the path, thread-pinned to one core. In isolation the engine processes a command in p50 2.05 µs (mean 1.27–1.42 µs across seeds) and sustains **630,000–690,000 commands a second**. That's the same ~2 µs scale as the wire run's engine clock, which means the 20k I measured on the wire was not the engine giving out. It was idling at a fraction of its capacity while something downstream throttled it. Two caveats on that number: it's the engine with durability stripped out, so it's a compute ceiling, not the durable-system ceiling (the journal costs more, and I pin down how much below). And a narrower micro-bench of just the book's insert/match/cancel path runs faster still, 2.2M/s, the number in the ablation table below. Different harnesses, different questions; don't multiply them together.

The wire telemetry says the same thing from the other side. At every rate I drove the rig — up to 150,000 orders a second nominal — the inbound ring depth stayed at zero. Of everything the engine was handed, it never fell behind. Nothing on the ingress-to-match path was the wall.

<NewTopology />

The wall is on the output side. The engine publishes each event into an outbound ring; a projection task drains that ring and fans every event out to 250 per-client lanes. Each reliable lane is capped, and when a client can't keep up its lane fills, so rather than silently drop a message the projection *evicts* that client. Past the saturation knee, all 250 overflow and evict at once. What corrected my mental model: I'd assumed the engine would end up spinning on a full outbound ring. It never does. Across the whole ladder, `outbound_full` stayed at zero while evictions hit 250 — the projection drains the ring faster than the engine fills it, so the backup is entirely downstream, at the per-client lanes.

| offered/s | achieved/s | in-sys p99 | evictions |
|---:|---:|---:|---:|
| 2,000 | 1,795 | 16 µs | 0 |
| 10,000 | 8,973 | 16 µs | 0 |
| 20,000 | 17,974 | 33 µs | 0 |
| 25,000 | 20,451 | 4.2 ms | **250** |
| 150,000 | 20,941 | 4.2 ms | **250** |

Microsecond latency and zero evictions through 20k, then a cliff at 25k where all 250 clients evict at once and the client-observed p99 jumps into the low milliseconds. That jump is not matching slowing down: with ring depth zero and a ~1.4 µs loop, nothing on the ingress-to-match path can produce milliseconds. It's the fan-out to 250 subscribers falling behind while the engine underneath stays at ~16 µs. A ceiling imposed by egress delivery, not by the engine.

The obvious objection: maybe 20k was just my single load box again, the v1 mistake round two. So I built the thing I'd wished for during the v1 post-mortem, a distributed load generator that hands disjoint slices of the 250-client roster to worker processes on separate machines and merges their latency histograms losslessly (power-of-two buckets sum exactly; quantiles get recomputed on the merged histogram, never averaged). Three worker boxes did not move the plateau — still ~20,500 orders a second. So the wall was never my sender. Three more senders couldn't help, because the constraint is how many receivers one engine box has to keep in sync.

To find which part of the fan-out binds, I profiled the engine box under a saturating 60k. Two threads pegged near 100%: the match core, which spins by design, and exactly one worker. The other six sat between idle and a quarter. That one pegged worker is the projection — the single task draining the outbound ring and routing each event to the right one of 250 lanes. The tasks that actually serialize and write to sockets were spread across the idle workers, nowhere near saturated. So the wall isn't the socket writes or the wire format; it's one thread doing the routing, serially. The fix is to shard it across cores, which the ring design makes safe — the same sharding that dropped and reordered updates in v1, except this time the structure holds.

## Which design choice actually mattered

Since the wire couldn't see the engine's ceiling, I stopped measuring through the network and asked a narrower question in-process: of the choices that make the engine fast, which one actually matters?

The way to answer that is to break each one on purpose. I built regressed variants — undo exactly one design decision, hold everything else fixed, replay an identical five-million-command stream — and measured the delta. Every variant produced a byte-identical 2,706,139 fills, which confirms the input was identical across cells. (One seed, so no run-to-run variance bars. The ablation changed only speed, never the answer, which is exactly the guarantee the reference book buys.)

The profiler kept pointing at allocation, so I started there. The clean way to isolate the arena is to hold the book shape constant and flip only the allocator — the bottom two rows below, both `BTreeMap`, one on the pooled arena and one allocating each price level on the heap.

| variant | book shape | hot-path alloc | throughput | p50 | p99 |
|---|---|---|---:|---:|---:|
| shipped | flat array | pooled arena | 2,207,254/s | 512 ns | 2,048 ns |
| swap array → `BTreeMap` | `BTreeMap` | pooled arena | 1,973,341/s | 512 ns | 2,048 ns |
| also arena → heap | `BTreeMap` | per-level heap | 375,194/s | 1,024 ns | 131,072 ns |

Dropping the arena — those bottom two rows, book shape fixed — cost **×5.3 in throughput** (1,973,341 → 375,194) and **×64 in tail latency**, p99 from 2 µs to 131 µs. That's the dominant lever by a wide margin, and the reason the tail specifically detonates is worth stating: an allocator call can wander off into unbounded work (coalescing free lists, a syscall into the kernel for more memory) while handing out a pre-reserved pool slot is bounded and constant-time every time. One honesty note: this delta is measured on the `BTreeMap` shape, because I never built the array-on-heap corner — nobody would ship it. So ×5.3 is the allocation cost on a tree of boxed nodes; on the flat array it would differ in the exact multiple, not the direction.

Then the array-vs-tree shape, with allocation held constant — the top two rows. The flat array bought **×1.12 throughput and identical p50/p99**. Real, worth keeping, and a small fraction of the allocation win. Part of why it's small is the ladder: at 99 price levels the whole tree fits in cache, so the array's asymptotic edge barely shows. The shape is the clever part, the one I'd have put on a slide. The measurement says the arena underneath it was doing most of the work. (The latency columns here use power-of-two buckets, so the clean ×2 and ×64 ratios are coarse bucket-edge artifacts; throughput is the precise signal.)

Then the journal, on a real xfs disk:

| journal commit | throughput | p50 |
|---|---:|---:|
| group-commit (batch of 64) | 32,299/s | 0.26 µs |
| per-command `fsync` | 508/s | 2.10 ms |

Group-commit is **×63.5**. Per-command durability means a real 2.10 ms disk `fsync` on the path of every single order; batching amortizes it to nothing. That's the concrete cost behind "durability off the hot path" — 2 ms per order if you get it wrong.

One thing I didn't measure: I never isolated the lock-free ring against a mutex-guarded book as a throughput ablation. The single-writer ring earns its place a different way, through the inbound-ring depth staying at zero under load plus the model check, not a regressed branch. So the measured trio is allocation, shape, and journal; the ring stands on correctness evidence, not a speed delta.

The takeaway: the array-shaped order book is the part I'd have shown off, and when I finally measured it, it was worth 12%. Not allocating on the hot path was worth 5.3×. I'd have bet on the shape from the design alone, and I'd have been wrong. The win you can draw on a whiteboard is rarely the one that dominates the profile — you have to break each piece and watch the clock to find out which.

## What ran the event

v1 ran the actual event. 150 traders, four racer-markets a race, standings on the projector, held together on a deploy path I would not call robust — a watchdog script and a quick-tunnel. None of the v2 work is a knock on it. Getting a working exchange in front of 150 people, on a first attempt at anything like it, is the reason there was a second version worth building. v2 only exists because v1 ran the race first.

## What I'd do next, and what I'd do differently

The profile handed me the next move: the projection is one thread doing all the routing, pegged while the other cores idle. Sharding it — one projection per group of lanes, each on its own core — is the obvious lift, and this time the ring design makes it safe rather than a source of races. That, plus a few percent of CPU currently going to tracing calls on the hot path, is where the next throughput lives. Only then does the engine's real single-core wire ceiling become measurable, because only then does something other than egress bind first. (The engine also busy-spins a full core even at idle. That's fine when it owns a pinned core for a live event, wasteful if I wanted many books per box, and the first thing I'd revisit for a different deployment.)

There's a co-constraint I haven't ruled all the way out, and I'd rather name it than pretend it away: the journal's group-commit tops out around 32k commands a second on the disk I measured, only ~1.5× above the wire plateau. The wire runs never backed the journal up (inbound depth stayed at zero, which it wouldn't if the journal were stalling), so it isn't the current wall. But on a slower disk it could become one before egress does, and any serious "how fast can one core really go" run has to watch the journal thread as closely as the projection.

Two things I'd do differently starting over. First, I'd build the distributed load harness first, not after a single-box run sent me chasing a ceiling that was really my load generator — I made the v1 mistake's cousin a second time before I caught it. Second, I'd have wired one honest end-to-end throughput number — acked, offered, and rejected, all three — into the harness from day one, instead of leaning on an acked-only rate that reads like loss until you know it's cancels. Both are the same lesson in different clothes: the measurement apparatus is part of the system, and it lies in exactly the ways you didn't instrument.

The bigger decision I'd make the same way is the risk model. v2's collateralized worst-case-loss model is more faithful to how a real prediction market works — you post what you could lose, you can't take a position you can't cover — but the competition ran on v1's flat ±100 position limit, and that difference changes how the game feels. A new player under a position limit walks up and swings to the cap without thinking about margin; under collateral, they have to understand reserve-and-settle before they can do anything. More correct, less fun at a party. I went with collateral anyway and let the four-trait seam hold the escape hatch: the risk model is one trait impl, so the party-game position-limit variant is a drop-in for whoever wants it, without touching the engine that earns the correctness guarantees.

The speed didn't come from Rust being faster than Python. It came from the design, and the biggest single piece of it was the least glamorous one: never allocating while matching. What kept surprising me is how often the fast decision and the correct decision were the same decision. The single writer is race-free because one thread owns the state, and lock-free for the same reason. The journal is durable because it sits in front of the engine, and off the hot path for the same reason.

The code is public — clone it, run the same harness, and you'll get the same plots (the single-box ones, at least; the multi-box numbers need four machines). And when I shard that projection and finally watch the engine top out on the wire instead of the fan-out, that's the next post.
