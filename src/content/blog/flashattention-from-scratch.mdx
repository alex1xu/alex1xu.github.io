This is part of a [summer I'm spending](/blog/blog-motivation) going deep on ML systems. The three weeks before this I spent learning CUDA fundamentals and FlashAttention, mostly out of [GPU MODE](https://www.youtube.com/@GPUMODE) lectures, Stanford's [CS336](https://stanford-cs336.github.io/), the PMPP book, and the FlashAttention papers ([FA1](https://arxiv.org/abs/2205.14135), [FA2](https://arxiv.org/abs/2307.08691)). I took CS 152, the upper-division computer architecture class, at UC Berkeley this past spring and have previously worked with Trainium and NKI, so a lot of the ideas came naturally. But it's one thing to read about how to program GPUs, and another to actually do it, and make a kernel go fast.

<Callout type="lesson" title="TL;DR">
"FlashAttention is fast" bundles two separate wins, which initially wasn't super clear to me, but building it forced them apart.

- **Tiling fixes memory, and on its own it made my kernel 11× slower.** Never materializing the `N×N` scores drops the footprint from O(N²) to O(N). My tiled kernel ran `N=16384` in **2.15 GB** where the naive version needed ~137 GB and ran out of memory. But that kernel did **5 TFLOP/s** against the naive baseline's **54**, because it runs its arithmetic on the general-purpose cores while naive's matmuls go straight to cuBLAS's tensor cores.
- **Going fast is the second win, and the online-softmax trick has little to do with it.** Adding tensor cores got me to **~21 TFLOP/s, about 10% of PyTorch's SDPA** (~200 TF). I had a few ideas about the rest of the gap. When I ablated the online-softmax (which many tutorials spend their length on), it came to **~2% of the runtime** in my kernel.
- **Programming is hard 😭** I spent hours debugging nothing because a kernel never launched and the GPU swapped underneath me.

This is the forward pass, measured on one A100. The backward pass and the Hopper FA3/4 are left to a follow-up.
</Callout>

Everything here ran on a single **A100-SXM4-80GB** (108 SMs, 2.0 TB/s HBM, 312 FP16 tensor-core TFLOP/s) on Lightning AI (thanks for the free credits!). Every TFLOP/s number is the attention FLOPs at `B=8, H=16, N=4096, d=128`, fp16, non-causal, timed with CUDA events. "SDPA" is PyTorch's flash backend on the same shapes.

## The memory wall

Before writing a single kernel I wrote the naive baseline to get a better my understanding of the problem (and solution).

<CodeCard file="naive.py">
```python
def naive_attention(q, k, v):
    # q,k,v: [B, H, N, d]
    d = q.shape[-1]
    scale = 1.0 / math.sqrt(d)
    s = (q @ k.transpose(-2, -1)) * scale # [B, H, N, N]  <- the problem
    p = torch.softmax(s, dim=-1)
    return p @ v
```
</CodeCard>

For the `[B, H, N, N]` scores tensor, at `B=8, H=16, N=8192` in fp16 it's `8·16·8192·8192·2` bytes, which is **17 GB** for one intermediate. Softmax reads the scores to write the probabilities, so both are resident at once and you hold it twice. I swept sequence length:

<MemoryWall />

Even on an 80 GB A100, naive attention falls over at `N=16384`. The scores are ~69 GB on their own, and ~137 GB once softmax holds the second copy. Shrinking the batch buys you room, since the tensor is linear in `B·H`, but it doesn't remove the wall. The blowup is O(N²) in sequence length, so a longer context walks you back into it at any batch size and you trade away throughput to get there.

FlashAttention's claim is that you never have to materialize that tensor at all. You tile it, keep a running softmax, and the memory drops from O(N²) to O(N).

<TilingSchematic />

It isn't what also makes it fast! And that surprised me.

## The algorithm in one paragraph

Online softmax (Milakov & Gimelshein, [2018](https://arxiv.org/abs/1805.02867)) computes a softmax in a single streaming pass with a running max `m` and running denominator `l`, rescaling the partial result whenever the max moves. FlashAttention ([Dao et al. 2022](https://arxiv.org/abs/2205.14135)) wraps that in a tiling loop. Load a block of Q, stream blocks of K and V through fast on-chip SRAM, accumulate the output block as you go, and never write the scores to HBM. I'm not going to re-derive it, because the [paper](https://arxiv.org/abs/2205.14135) and [GPU MODE Lecture 12](https://www.youtube.com/watch?v=zEuwuCTEf_0) already do it better than I can.

Here's the whole algorithm in plain PyTorch, which I wrote first as a numerical oracle to check the CUDA against. It streams K/V in blocks and never holds more than one block of scores.

<CodeCard file="tiled_ref.py">
```python
def tiled_attention(q, k, v, block_k=128):
    B, H, N, d = q.shape
    scale = 1.0 / math.sqrt(d)
    m   = torch.full((B, H, N, 1), float("-inf")) # running max
    l   = torch.zeros((B, H, N, 1)) # running denom
    acc = torch.zeros((B, H, N, d)) # unnormalized output
    for j in range(0, N, block_k):
        kj, vj = k[:, :, j:j+block_k, :], v[:, :, j:j+block_k, :]
        s = (q @ kj.transpose(-2, -1)) * scale # [B,H,N,bk] — one block of S only
        m_new = torch.maximum(m, s.max(dim=-1, keepdim=True).values)
        alpha = torch.exp(m - m_new) # rescale factor when the max moves
        p = torch.exp(s - m_new)
        l   = alpha * l   + p.sum(dim=-1, keepdim=True)
        acc = alpha * acc + p @ vj
        m = m_new
    return acc / l # divide by l once, at the very end (the FA2 choice)
```
</CodeCard>

Dividing by `l` once at the end, keeping the accumulator unnormalized through the whole loop, is one of the choices that separates FlashAttention-2 from -1. Both keep the max-rescale `alpha = exp(m - m_new)` every block, because you can't avoid it when a later block raises the running max. What FA2 drops is the per-block normalization, the divide by `l` that FA1 does on every block (FA2 defers that single division to the end). The point of the move is to cut non-matmul work off the inner loop (we look at how much this is worth in the profiling later).

## Win #1: tiling fixes memory, but made it 11× slower

My first kernel is the simplest thing that tiles correctly. One CUDA thread per query row, K and V staged into shared memory a block at a time, the online-softmax recurrence in scalar floating-point. One thread to a row means the arithmetic runs on the general-purpose CUDA cores and the tensor cores sit idle the whole time. That isolates memory discipline from fast compute.

<CodeCard file="flash_min.py">
```cuda
for (int j = 0; j < N; j += BLOCK_N) {
    // cooperative load of this K/V tile into shared memory
    // … (every thread helps stage Ks[], Vs[]) …
    __syncthreads();

    for (int kk = 0; kk < BLOCK_N; ++kk) {
        // score for this key: s = scale * dot(qreg, Ks[kk])
        float s = 0.f;
        for (int t = 0; t < HEAD_DIM; ++t) s += qreg[t] * __half2float(Ks[kk*HEAD_DIM + t]);
        s *= scale;

        // online-softmax update for one key (the scalar recurrence)
        float m_new = fmaxf(m, s);          // running max
        float alpha = __expf(m - m_new);    // rescale old state to the new base
        float p     = __expf(s - m_new);    // weight of this key
        l = l * alpha + p;
        for (int t = 0; t < HEAD_DIM; ++t)
            acc[t] = acc[t] * alpha + p * __half2float(Vs[kk*HEAD_DIM + t]);
        m = m_new;
    }
    __syncthreads();   // don't overwrite smem until everyone's done reading this tile
}
```
</CodeCard>

Max abs error against PyTorch's `scaled_dot_product_attention` is ~1e-3 in fp16 (it works). More importantly this kernel shows tiling alone fixes the wall. It ran `N=16384` at **2.15 GB**, exactly where the naive version needed ~137 GB and died.

And it runs at **~5 TFLOP/s. The naive baseline does 54.** Naive is slow on memory, but its two big matmuls go straight to cuBLAS's tensor-core kernels, which my scalar loop can't touch. So on its own, tiling for memory made the kernel **11× slower**. Turns out fitting and going fast sit on different axes! And fixing the first costs the second.

## Win #2: adding tensor cores

The second kernel keeps everything in registers and shared memory and does both matmuls, `Q·Kᵀ` and `P·V`, on the tensor cores via WMMA. WMMA is the CUDA API for handing the tensor cores 16×16 tiles as fragments and getting their product back. Here, I also switched to the FlashAttention-2 loop order. This allows one warp to own a block of 16 query rows on the outside and stream the K/V blocks through on the inside, keeping its running `(m, l)` and output accumulator local and normalizing by `l` exactly once at the end.

Before wiring the whole thing together I tested the `Q·Kᵀ` matmul on its own and got 1.9e-5 against PyTorch, so that when the fused kernel was wrong I'd know it wasn't the tensor-core fragments or the transpose trick. You feed K as a column-major fragment, which reinterprets the same row-major buffer as `Kᵀ` with no data movement.

<CodeCard file="flash_wmma.py" collapsible summary="The FA2-schedule inner loop (WMMA)" lines="40–94">
```cuda
for (int j = 0; j < N; j += 16) {
    // ---- S = Q @ K^T  (WMMA, fp16 in, fp32 accumulate; col_major K = the transpose) ----
    wmma::fragment<wmma::accumulator,16,16,16,float> cs;
    wmma::fill_fragment(cs, 0.f);
    for (int kk = 0; kk < NK; ++kk) {
        wmma::fragment<wmma::matrix_b,16,16,16,half,wmma::col_major> kb;
        wmma::load_matrix_sync(kb, Kb + kk*16, HD);
        wmma::mma_sync(cs, qa[kk], kb, cs);
    }
    wmma::store_matrix_sync(Ss, cs, 16, wmma::mem_row_major);
    __syncwarp();

    // ---- online softmax, one row per lane ----
    if (lane < BM) {
        int r = lane;
        float rowmax = /* max over the 16 scaled scores: scale * Ss[r*16+c] */;
        float m_new = fmaxf(Ms[r], rowmax);
        float alpha = __expf(Ms[r] - m_new);
        float rowsum = 0.f;
        for (int c = 0; c < 16; ++c) {
            float p = __expf(scale * Ss[r*16 + c] - m_new);
            Ps[r*16 + c] = __float2half(p);
            rowsum += p;
        }
        Ls[r] = alpha*Ls[r] + rowsum;  Ms[r] = m_new;  Al[r] = alpha;
    }
    __syncwarp();

    // ---- PV = P @ V  (WMMA over the head-dim sub-tiles) ----
    wmma::fragment<wmma::matrix_a,16,16,16,half,wmma::row_major> pa;
    wmma::load_matrix_sync(pa, Ps, 16);           // the probabilities we just wrote
    for (int nt = 0; nt < NK; ++nt) {
        wmma::fragment<wmma::matrix_b,16,16,16,half,wmma::row_major> vb;
        wmma::load_matrix_sync(vb, Vb + nt*16, HD);
        wmma::mma_sync(pv, pa, vb, /*zero acc*/);  // -> PVs[nt block]
    }
    // ---- O = alpha*O + PV : rescale the running output, then add this block ----
    for (int t = lane; t < BM*HD; t += 32) Os[t] = Al[t/HD]*Os[t] + PVs[t];
    __syncwarp();
}
// normalize once at the very end: O[r] = Os[r] / Ls[r]
```
</CodeCard>

Max abs error against SDPA lands between **1.2e-4 and 4.9e-4** across shapes from `N=16` up to `B=4,H=8,N=2048`, both fp16.

<Callout type="note" title="Tiling done right buys accuracy back">
I expected tiling to trade a little accuracy for the memory savings, since I'm summing a softmax in pieces. The opposite happened for this kernel. Its max error is ~1.2e-4 against naive's ~6e-4, because the running `m`, `l`, and output accumulator all live in fp32 while the inputs are fp16, so the block-to-block accumulation never rounds through fp16. What actually buys the accuracy is carrying that accumulator in fp32 across blocks. My earlier scalar tiled kernel skipped that and landed a bit worse than naive (~1e-3), so tiling on its own isn't where the precision comes from.
</Callout>

So I had tensor cores, the real FA2 schedule, and numerical correctness. The kernel above, one warp and 16 keys per block, runs at **~14.7 TFLOP/s, about 7% of SDPA**, still 3.7× slower than the naive baseline I was trying to beat. Widening the K/V block to 64 keys amortizes each softmax update over more work and lifts it to **~21 TFLOP/s**, a real ×1.44. But that's where it plateaus.

Tensor cores were necessary, but surprisingly to me nowhere near sufficient. The remaining gap from 21 to SDPA's ~200 was really interesting.

## Three hypotheses

I had three ideas about why a correct tensor-core kernel was still only 10% of SDPA, and how to bridge the gap.

### Idea 1: amortize the softmax over bigger tiles

With a 16-wide K/V block, the per-block softmax bookkeeping runs once per 16 keys. Widen the block to 64 and it runs a quarter as often, so if the bookkeeping is the cost, a 4× wider tile should pay off big.

This was right in direction but wrong in size. Throughput went 14.7 → 21 TFLOP/s, a ×1.44. A 4× wider tile bought only ×1.44, which means most of the runtime scales with the tile too. If the bookkeeping were the cost, amortizing it 4× should theoretically pay 4×. Only getting a quarter of that tells me the real cost is in the streaming the wider tile also grew.

### Idea 2: raise occupancy

One warp per block is about 3% occupancy, so the SMs looked starved for warps to hide memory latency behind. I put four warps on a block and opted into dynamic shared memory to fit them.

Occupancy rose to 8 warps per SM, but throughput actually **fell about 21%**, from 21 TF to ~16.6. To me, adding warps seemed to be the standard fix for a *latency*-bound kernel, so if latency-hiding were the issue, more warps should have helped, but instead it hurt. I think what happened was that because in my schedule each warp owns its own Q-block and streams all of K and V for it, four warps on a block re-read K and V four times over instead of sharing them. On a kernel that's already moving too many bytes, the extra warps multiply the traffic.

### Idea 3: the softmax glue is the cost

After the first two ideas, I stripped the online-softmax work out of the kernel entirely (the `exp`, the running max, and the rescale) and re-timed against the full kernel, as well as against a variant with just the `exp` removed.

<RuntimeSplit />

At `N=4096` the full kernel is 52.0 ms and the no-softmax kernel is 51.0 ms. The online softmax, it turned out, was only **~2% of the runtime** here. Removing the `exp` alone does nothing measurable. The algorithm was not the bottleneck.

Although individually ineffective, I think the results of all three experiments actually point to the same root cause. Bigger tiles helped a little and then plateaued, more warps made it worse by multiplying K/V reads, and the softmax is 2%. What's left, is memory traffic. My kernel re-streams all of K and V from global memory for every 16-row Q-block, so it moves far more bytes than the algorithm requires, and that's the cost the tile-size and occupancy knobs were both really touching. Due to limitations on Lightning AI (and other providers) I couldn't run `ncu` to read the stall counters, so this is just my leading hypothesis that is consistent with all three results.

FA2's move is to cut non-matmul work off the inner loop, and my ablation says non-matmul work is 2% of this kernel, so that optimization is in the noise here. However, I'm only running at 10% of peak, which stretches the denominator and shrinks every non-matmul slice. On A100 the softmax `exp` runs on the SFU at roughly 1/16th the tensor cores' fp16 throughput, so per FLOP it's about 16× more expensive than a matmul FLOP. Push the matmul toward peak and that 2% climbs. Minimizing it (FA2) and hiding it behind the tensor cores (FA3's warp specialization) is exactly what you do once the matmul is no longer leaving 90% of the machine on the floor. I'm just not there yet, so I get to see the softmax as free.

## Most of the time went to things other than the math

I made two rookie mistakes that both wasted a chunk of my day.

<details class="aside">
<summary>Aside: hours lost to a kernel that never launched</summary>

For most of a day my WMMA kernel produced wrong output across about ten configs, and the symptoms kept shifting. Same input, different runs, `0.54`, then `NaN`, then `0.29`, then all zeros. The one pattern was that the garbage depended on the total allocation size, not the tensor shape. I went hunting for a numerical bug in the softmax, then an indexing bug, then a race.

There was no compute bug. The kernel had never launched, not once. The launch was failing silently with `cudaErrorInsufficientDriver`, because the system `nvcc` was CUDA 13.0, which the host's driver (570) can't run, while torch works because it bundles its own 12.8 runtime. Every "result" I'd been debugging was the output tensor's initial value, uninitialized memory, whatever happened to be in that allocation pool. The allocation-dependent NaN was the tell, because it was memory the kernel never touched.

```diff
  flash_wmma<<<grid, 32>>>(/* … */);
- return o;   // trusting output from a launch that may have silently failed
+ cudaError_t e = cudaDeviceSynchronize();
+ TORCH_CHECK(e == cudaSuccess, "launch failed: ", cudaGetErrorString(e));
+ return o;
```

I will make sure to run this check in every kernel harness I write now.

</details>

<details class="aside">
<summary>Aside: the GPU changed under me</summary>

My memory sweep reported a 78.9 GB allocation as "OK" on what my environment check said was a 40 GB card. My first instinct was memory oversubscription, host paging making an over-large allocation look like it fit.

It wasn't. The Lightning instance had swapped from a 40 GB A100 to an 80 GB one between sessions. `N=12288` took 1.07s against `N=8192` at 0.30s, about 3.5×, in line with the 2.25× FLOP ratio plus a memory-bound penalty, and nowhere near the 5–20× slowdown host paging would cause. `torch.cuda` confirmed 85 GB of total memory. On an ephemeral cloud GPU the machine itself isn't a constant, so I need to remember to re-verify it every session now.

## Where this leaves the forward pass

The forward pass is correct in three versions that each fix one more thing, and the two wins are cleanly separated.

| kernel | TFLOP/s | what it proves |
|---|---|---|
| naive | 54 | the O(N²) memory wall (dies at N=16384) |
| tiled, no tensor cores | 5 | tiling fixes memory (2.15 GB @ N=16384) and nothing else |
| WMMA, FA2 schedule (best) | 21 | tensor cores are necessary, ~10% of SDPA, not enough |
| PyTorch SDPA (flash backend) | ~200 | the target, ~65% of the card's peak |

The bar I set going in was a correct FA2-scheme kernel benchmarked against SDPA. I think The real fix is a register-resident kernel that stages K/V once and hands the tensor cores bigger, better-fed tiles, which is the `mma.sync` plus swizzled-shared-memory rewrite. I stopped short of that here. Chasing SDPA parity is probably hours of `mma.sync` tuning.

The memory-wall plot only measures allocation and does not measure HBM traffic. An ideal FA kernel reads Q, K, and V about once, so its traffic is O(N), but mine re-streams all of K and V for every Q-block, so the bytes it *moves* are closer to O(N²) even though the bytes it holds stay O(N). Pinning down the traffic exactly needs the DRAM counters `ncu` gives, which I couldn't run here.

## What's next

Two things this post skips, coming in a follow-up (eventually). The backward pass is the harder half. It has the `D = rowsum(dO ∘ O)` preprocessing trick, it recomputes the scores block by block instead of storing them, trading FLOPs for the HBM a materialized-`S` backward would cost, and it splits into a dK/dV loop and a dQ loop. I will probably do it in Triton.

The FA3/FA4 frontier is the other one. The gap I hit, a kernel spending its time moving K/V instead of feeding the tensor cores, is what Hopper's Tensor Memory Accelerator and warp specialization were built to close, with dedicated async-copy hardware for the loads and a producer/consumer split that overlaps them with the matmul.

To be honest writing raw kernels is probably not the layer I'm most drawn to, and that's a big part of why this one took me so long to finish. The parts of the stack I want to spend more time in sit a bit higher up, so I'm leaving the backward pass and the FA3/4 write-up as things I'll come back to!
