[Part one](/blog/mario-markets) described the matching engine. In isolation it processed roughly 630,000–690,000 commands per second. With 250 connected clients, the full service initially stopped near 20,000 acknowledged orders per second. Matching was not the constraint. Delivering the engine's output was.

This was not one optimization. Each change exposed a different limit, and several changes that reduced real CPU cost did not move throughput at all.

## Start with the output contract

The exchange has two kinds of outbound traffic.

- **Reliable, client-specific events:** order acknowledgements, fills, and cancels. These must arrive in order. A slow client is disconnected rather than silently losing an event.
- **Market data:** current book snapshots and trades. This can be conflated. If a client misses one snapshot, the next one contains the current state.

Initially, every trade was sent as its own frame to every client. At 250 clients, that created a large number of frames and task wakeups. Batching trades into the 20 Hz market-data tick removed the eviction cliff: dropped market-data frames went from about one million per run to zero, and in-system p99 at 30k offered fell from 4.2 ms to 262 µs. It moved the sustained ceiling only from about 27k to 31k because reliable acknowledgements still dominated the frame count.

That distinction mattered throughout the investigation. A smaller or cheaper operation is not necessarily the operation limiting the system.

## A busy thread was not necessarily a busy engine

At the 31k plateau, one Tokio worker was fully utilized while several cores were mostly idle. It was the routing task that drained engine output and placed each event on the appropriate client lane. Most of that core's time was Tokio scheduling overhead rather than routing itself, so I moved the task to a dedicated busy-poll thread.

The change worked as intended: the task's CPU use fell from about 99% to 30%, freeing a core. Throughput did not change. That worker had been expensive, but it had not been the limiting stage.

The next profile made the engine look fully utilized. The same reasoning prevented a false conclusion. The engine's matching work was only a small fraction of samples. It spent most of its time busy-spinning on an empty input ring. It was not overloaded. It was starved of commands.

## A journal bug was blocking admission

The journal records sequenced commands for recovery. The design allowed a short window of acknowledged-but-unflushed commands after a crash, so the journal was never supposed to delay matching.

In practice, ingress first handed each command to a bounded journal path and only then handed it to the engine. The journal thread sometimes blocked in `fsync`. Once its queue filled, ingress stopped admitting orders and the engine spun on an empty ring.

<ExcalidrawDiagram name="backpressure-evidence" alt="Before the fix, orders went through a journal fsync before reaching the engine, so the queue could fill and leave the engine idle. The server receive queue reached 126 MB. After the fix, orders reach the engine while a copy goes to the journal." caption="The server's 126 MB receive queue showed that the engine was not receiving orders. The journal remains behind the engine after the change." />

This was hard to see in a CPU flamegraph. `fsync` waits on storage in the kernel, so the journal thread is off CPU and receives few samples. The busy-spinning engine, meanwhile, looks hot even while it has no work.

The fix was to restore the intended independent tee: ingress gives the command to the engine immediately and sends a copy to the journal separately. The journal group-commits writes in the background. This moved the ceiling from about 31k to 54k orders per second.

This change also exposed a correctness consideration that the replay tests did not cover. Enlarging a journal batch can widen the duration of the acknowledged-but-unflushed window under sustained traffic. Replay proves that persisted input reproduces the engine. It does not prove how quickly an acknowledgement becomes durable. The durability window needed its own bound and test.

## Locate queues before changing code

At the next plateau, several plausible fixes did not move throughput. Moving routing off Tokio had freed a core. Replacing deep per-event copies with `Arc`, Rust's standard atomic reference-counted pointer, removed copying under a lock. Neither changed the knee.

The useful measurement was socket queue depth, collected with `ss` on the server and load generators.

The server had 126 MB of unread orders in its inbound socket queue, while its outbound queue was small and the load generators' queues were nearly empty. The generators were sending and reading correctly. The server was failing to read incoming orders because a downstream delivery stage was holding up the pipeline.

This also explained an apparent network-latency discrepancy. In-system timing began only after the server read a frame from its socket. Time spent waiting in the server's own inbound socket queue was therefore reported by the client as network time, even though it was local queueing.

## The delivery stage was serial

The output ring already let several consumers read the same ordered event stream through independent cursors. But only one delivery consumer existed. It routed every event for every client, one after another, so it set the ceiling even when other cores were available.

<ExcalidrawDiagram name="delivery-shards" alt="Before sharding, one consumer routed all events to 250 client lanes. Afterward, four consumers each have an independent cursor and own clients selected by user ID modulo four." caption="Each client remains assigned to one delivery shard, so its events still arrive in order." />

I split clients into four delivery shards using `user_id % 4`. Each shard owns its subset of clients end to end: its ring cursor, client lanes, and delivery state. Every shard reads the ordered event stream, but routes only events for its own clients. A client always remains on one shard, preserving client-level event order without shared locks.

The leaderboard was replicated rather than shared. That is safe because every shard sees the same deterministic event stream and derives the same value. The one non-idempotent settlement write ran only on shard 0.

Sharding moved the clean end-to-end ceiling from about 54k to 97k orders per second. At that point the single pegged delivery consumer was gone. Work was spread across the delivery shards and socket-writing workers.

## Fix the measuring instrument too

Above about 80k offered orders per second, the load generators became a new limit. They fully parsed every market-data frame, including 99-level snapshots sent 20 times per second to each simulated client, even though the benchmark used only acknowledgements, fills, rejections, and sequence counters.

The fix was to keep reading every frame—otherwise the server's egress behavior would no longer be under test—but to parse only a small header for frames the benchmark did not use. Full parsing remained for reliable events. With that change and more generator machines, the test rig stopped limiting the system and the 97k result was measurable.

One final experiment reinforced the same point. Reducing market-data snapshots from roughly 49 levels per side to 10 barely moved the ceiling, from 97.3k to 97.7k. At that rate, the reliable lane sent about 97,000 acknowledgement frames per second while market data sent about 5,000 snapshots. Frame count, not snapshot size, was the meaningful cost.

## What changed, and what did not

The major capacity gains came from two structural changes:

- Decoupling journal `fsync` from order admission: roughly 31k to 54k orders per second.
- Sharding client delivery across four cores: roughly 54k to 97k orders per second.

Batching market data was still necessary because it removed a separate slow-client failure mode. Moving routing off the async runtime and removing deep copies were still correct cleanups. They just did not set the throughput limit at the time they were made.

The broader lesson was to treat performance as a queueing problem, not a list of expensive functions. CPU profiles show where code runs. They do not directly show blocked I/O, serial ownership, or queues outside the process. The engine's matching loop was fast from the beginning. The work was finding where the surrounding system prevented it from receiving or delivering work.
